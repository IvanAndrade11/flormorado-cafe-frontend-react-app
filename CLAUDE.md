# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flormorado Café — a React 19 + TypeScript SPA e-commerce site for a Colombian specialty-coffee brand, deployed to production at flormoradocafe.com via GitHub Pages. Spanish is the language used throughout UI copy, comments, and content data files.

## Commands

```bash
npm start                # dev server at localhost:3000 with HMR (webpack-dev-server)
npm run build            # production bundle to dist/
npm run preview          # serve dist/ locally to sanity-check a production build
npm run deploy           # build + write dist/CNAME + publish dist/ to gh-pages branch
npm run prettier         # format src/**/*.{ts,tsx,js,jsx,json,css,scss,md}
npm run prettier:check   # check formatting without writing
npm run lint             # ESLint over src/**/*.{ts,tsx}
npm run lint:fix         # ESLint with --fix
npm test                 # run the Jest suite once
npm run test:watch       # Jest in watch mode
npx tsc --noEmit         # type-check without emitting (no dedicated npm script)
```

To run a single test file, pass it to Jest directly: `npx jest src/utils/constants/store/order.test.ts`.

Tests live colocated with the source they cover (`Thing.ts` + `Thing.test.ts` in the same folder), using Jest + `@testing-library/react` with a `jest-environment-jsdom` environment; `jest.config.js` mirrors the `@/*` path aliases from `tsconfig.json`/`webpack.config.js` and stubs SCSS/asset imports (see `src/__mocks__/fileMock.js`) since Jest can't process them the way webpack does.

Component tests need two pieces of setup that are easy to break without noticing: `jest.setup.ts` polyfills `TextEncoder`/`TextDecoder` (React Router 7 reads them at import time and jsdom doesn't provide them), and `src/types/jest-dom.d.ts` re-imports `@testing-library/jest-dom` so `tsc` sees matchers like `toBeInTheDocument` — `jest.setup.ts` lives outside `src`, and `ts-loader` type-checks test files as part of `npm run build`, so without that file a component test breaks the build even though it passes under Jest. `jest.config.js` also ignores `.claude/`, because background Claude sessions create full repo copies under `.claude/worktrees/` that Jest would otherwise pick up.

`.github/workflows/ci.yml` runs `tsc --noEmit`, lint, format check, tests, and build on every PR to `main` and every push to `main` — treat a red CI check the same as a local failure.

## Commit messages

Follow the existing history's convention, one line, no body:

```
:gitmoji: TICKET-ID: short lowercase description, no trailing period
```

- `TICKET-ID` is the Jira-style ticket the branch is for (e.g. `FMC-0010`), matching the `feature/TICKET-ID` branch name.
- Keep the description short and imperative (e.g. `fix loader stuck when flag never resolves`, not a multi-sentence explanation).
- Pick the gitmoji by change type, matching prior usage in this repo: `:sparkles:` new feature, `:bug:` bug fix, `:lipstick:` UI/style only, `:memo:` docs, `:package:` deps/config, `:building_construction:` architecture/structural change, `:boom:` breaking change, `:wrench:` tooling/config.
- Do not add a commit body — if the change needs more explanation than the one-line subject, put that explanation in the PR description instead.

## Comentarios en el código

Un comentario dice **por qué**, nunca qué hace el código, y cabe en una línea; dos solo si no queda de otra. Nada de bloques de varias líneas ni de párrafos justificando una decisión encima de una función: ese contexto va en este `CLAUDE.md` o en la descripción del PR. Si el código necesita el comentario para entenderse, casi siempre lo que hay que cambiar es el código. Los comentarios largos que ya están en el repo son historia, no el patrón a seguir.

## Environment

Env vars are injected via `dotenv-webpack`, which picks the file based on webpack mode:

- `.env.development` → `npm start`
- `.env.production` → `npm run build`

Both files are gitignored (`.env.example` documents the variables). Key vars: `SDK_CNFCT` (ConfigCat SDK key), `ORDERS_API_URL` (base URL of the orders backend) and `TURNSTILE_SITE_KEY` (public key of the Turnstile widget, optional — see Anti-abuse below). These files must exist locally before running dev/build or webpack will fail to inject them.

`ORDERS_API_URL` falls back to the production Worker URL when unset (this version of `dotenv-webpack` replaces `process.env` with `{}`, so a missing key reads as `undefined`, not as a stub string). For local end-to-end work, point `.env.development` at `http://localhost:8787` and run the backend repo (`../flormorado-cafe-backend-orders`) with `npm start`; its `.dev.vars` must list `http://localhost:3000` in `ALLOWED_ORIGINS` or the browser blocks the response on CORS. `../.claude/launch.json` has both servers configured (`dev` and `backend`).

## Architecture

**Bootstrap chain** (`src/index.tsx` → `src/App.tsx`): `ConfigCatProvider` (feature flags, auto-polling every 10s) wraps `HashRouter` wraps redux `Provider` wraps `App`. `App` renders `Loader`, `Navbar`, the route `Router`, `Footer`, `ToastFmc`, `WhatsAppButton`, and the global `ShoppingCart` — the latter three are rendered app-wide outside the route tree, not per-page. `Navbar`/`Footer` sit outside the `Suspense` boundary so they stay mounted while a lazy route chunk loads; only `<Router />` is wrapped.

**Routing**: `react-router-dom` v7 con `HashRouter` (obligatorio en GitHub Pages, que no enruta del lado del servidor). Las rutas viven en `src/app/router/index.tsx` y las cadenas de ruta salen de `URLS` en `src/utils/constants`. Por el `HashRouter`, todo enlace interno queda como `/#/ruta`. Cada componente de ruta se carga con `React.lazy` (un chunk de webpack por página) y cada carpeta de página expone un barril `index.ts` que reexporta el componente por nombre y como `default` (`FMC-0031`), así que una ruta nueva se agrega con `lazy(() => import("@/pages/X"))`: sin `.then((m) => ({ default: m.X }))` y sin repetir el nombre en la ruta. El `default` vive en el barril, no en el archivo de la página, así que las páginas conservan un único export nombrado, que es el que importan sus pruebas. Ya no existe el barril `src/pages/index.ts`: nadie lo usaba y un import desde `@/pages` habría juntado todas las páginas en un solo chunk, rompiendo la carga perezosa.

**State management**: a single Redux Toolkit slice (`mainSlice` in `src/app/providers/redux/reducer.ts`) mounted at `store.main`. Shape (`IMainState` in `src/types/store`) has two top-level branches: `session` (loader, categoryTitle, showCart, toast, cart) and `flags` (raw ConfigCat flag values). There is no domain/entity state beyond the cart — product/blog/store content is not stored in Redux, it comes from static constants (see below).

Two ways to touch the store, both wired to the same slice:

- Inside components: `useAppDispatch` / `useAppSelector` from `src/app/providers/redux` (typed wrappers around react-redux hooks).
- Outside components (e.g. from `useInit`, plain modules): the pre-bound setter functions in `src/utils/constants/redux/sets.ts` (`setFlags`, `setLoader`, `setCart`, `setShowCart`, `setShowToast`, `setToastMessage`, `setCategoryTitle`), which call `store.dispatch` directly. Prefer these setters over dispatching action creators manually when outside a component's render, to stay consistent with the existing pattern.

**Feature flags**: `useFlags` (`src/hooks/useFlags.ts`) wraps `configcat-react`'s `useFeatureFlag` for each known flag (`testFlag`, `storeProducts`, `storeCategories`, `coffeeGrowers`, `blog`) and exposes an aggregate `loading` (true until every flag's own `useFeatureFlag` has resolved). `useInit` (`src/hooks/useInit.ts`) waits for that `loading` to turn false, then pushes the flags into Redux via the setters above — it's the single place flags cross from ConfigCat into app state. `docs/configCat/` has one annotated `.jsonc` per flag with the real remote structure — check it before parsing a flag instead of assuming its shape.

**Blog content**: `BlogPost` renders the remote `blog` flag's HTML body via `dangerouslySetInnerHTML`, but only after running it through `DOMPurify.sanitize(...)` — never render that HTML unsanitized, since it comes from a remotely-editable ConfigCat flag. `BlogPost` also applies the entry's SEO fields (`entry.seo.metaTitle`/`metaDescription`/`metaImage`, falling back to `title`/`excerpt`/`featuredImage`) to `document.title` and Open Graph meta tags via the reusable `useDocumentMeta` hook (`src/hooks/useDocumentMeta.ts`); reach for that hook on any other page that needs per-page SEO metadata.

**Content/data**: product, category, filter/sort, and navigation data are static TypeScript/JSON constants under `src/utils/constants/` (`store/data.ts`, `store/filter.ts`, `store/order.ts`, `common/data.ts`, `common/actions.ts`, `media/*`), not fetched from an API. `src/services/` holds the backend integrations, `orders/` and `contact/` (see Checkout and Contact below). When adding or changing store data (products, filters, sort options), edit these constant files rather than component code.

**Path aliases** (defined identically in both `tsconfig.json` and `webpack.config.js` — keep them in sync if changed): `@/*` → `src/*`, `@components/*` → `src/components/*`, `@pages/*` → `src/pages/*`, `@assets/*` → `src/assets/*`.

**Component layering** under `src/components/`: `common/` (generic, cross-app: Loader, ScrollToTop, Toast), `layout/` (page chrome: Navbar, Footer), `section/` (content sections/carousels used on Landing-type pages), `ui/` (interface widgets, including the `Store/` subtree for product cards, the shopping cart, and the product configurator). Each folder exposes an `index.ts` barrel; import from the barrel (e.g. `@/components/ui`) rather than deep-importing a component file directly, matching existing usage.

**Barriles y `sideEffects` (`FMC-0031`).** Importar desde un barril solo es gratis si webpack puede descartar lo que no se usa, y para eso tiene que saber que los módulos no hacen nada al importarse. Eso lo declara el campo `sideEffects` de `package.json`, que marca como efectivos únicamente `**/*.scss` y `**/*.css`. Sin ese campo, un solo `import { CarouselMessage } from "@/components/ui"` en un componente eager como `Navbar` arrastraba los 14 módulos del barril al chunk `main`: todo el UI de tienda (`StoreCard`, `CategoryCard`, `ProductGallery`, `ProductInfo`, `ProductConfigurator`, `NavbarStore`) se descargaba también para quien entraba al blog o a una página legal, y el `.mp4` de 3,4 MB que cuelga de `@/utils/constants` quedaba atado al entrypoint inicial. Con el campo, `main.js` pasó de 225 KiB a 195 KiB (77 KiB a 72 KiB con gzip) y las pantallas de tienda ganaron sus propios chunks (18 → 21). Dos cosas que conviene no romper: la lista tiene que seguir incluyendo los estilos, porque si se quita webpack descarta un `import "./X.scss"` de un componente que sí se usa y la pantalla se queda sin CSS; y si algún módulo de `src/` llega a hacer algo con solo importarse (registrar un polyfill, mutar un global), hay que agregarlo a la lista o dejará de ejecutarse en producción.

**El CSS de producción no lleva source map (`FMC-0031`).** `devtool: "source-map"` enciende por herencia el `sourceMap` de `css-loader`, y como `style-loader` inyecta los estilos desde el JS —no hay ningún archivo `.css`— ese mapa no puede vivir en un archivo aparte: `css-loader` lo incrusta en el módulo, como objeto con `sourcesContent`. Con Bootstrap eso significaba enviarle a cada visitante su `bootstrap.min.css.map` de 590 KB, es decir el SCSS completo de Bootstrap, dentro del bundle. Por eso los dos loaders reciben `sourceMap: !isProd`: en desarrollo los mapas siguen encendidos y depurar estilos no cambia, y en producción el JS inicial pasó de 1,83 MiB a 1020 KiB (de 502 KB a 376 KB con gzip). Los `.js.map` de JavaScript se siguen emitiendo como archivos aparte, que solo descarga quien abra las DevTools, así que depurar el JS de producción tampoco cambia. Lo único que se pierde es que el panel Styles atribuye las reglas al `<style>` inyectado y no a `Componente.scss`; para depurar un estilo que solo se reproduzca en el build de producción, se pone la opción en `true`, se reconstruye y se devuelve. El arreglo de fondo sería extraer el CSS a un `.css` real con `mini-css-extract-plugin`, que daría bundle chico y mapa a la vez.

**Cart behavior**: cart items live in Redux (`session.cart`, typed `ICoffeeProduct[]`) and are grouped/summed by grind type in the `ShoppingCart` component tree (`ProductListGroup`, `TotalView`, `BottomButtons`) — see `src/components/ui/Store/ShoppingCart/` before changing cart logic, since grouping-by-grind is the one non-obvious business rule in the cart. The cart is also persisted to `localStorage` (`fmc-cart` key, 14-day TTL) in `src/app/providers/redux/store/index.ts`, hydrated on store creation and re-saved on every cart change.

A cart line's `id` is **not** the catalog id: `ProductConfigurator` stores each line as `${product.id}-${grindingId}` so the same coffee in two grinds stays two lines, and `grinding` holds the grind option's id (`"gruesa"`), not its label (`"Gruesa"`). Anything that talks to the catalog or the backend must go through `getCatalogProductId` and `getGrindingLabel` in `src/utils/constants/store/cart.ts` — sending the raw line id makes the backend reject every order as an unknown product. The id is derived rather than stored separately so that carts already sitting in `localStorage` keep working. Totals come from `computeCartTotals` in that same file, which both `TotalView` and the order payload use: the backend recomputes the total with the same rules (free shipping from $150.000, shipping taken from the first cart line) and rejects the order if they disagree, so change them in both repos or not at all.

**Checkout**: `src/pages/Checkout/Checkout.tsx` drives a 3-step accordion (contact → delivery → payment) built from declarative field arrays in `src/utils/constants/common/forms.ts` (`CONTACT_FORM_FIELDS`, `DELIVERY_FORM_FIELDS`, `PAYMENT_FORM_FIELDS`), rendered generically by `CheckoutForm.tsx`. A field's `type` can be `"text"/"email"/"tel"` (plain `Form.Control`), `"select"`, `"checkbox"`, or `"note"` (an informational `Alert`, not real data); `showWhen`/`hideWhen` (`{ field, equals }`) make a field's visibility depend on another field's current value (e.g. the BRE-B confirmation note only shows when `paymentMethod === "bre_b"`). If the "guardar mi información" checkbox is checked, contact + delivery field values are persisted to `localStorage` (`fmc-checkout-info` key, no expiry) and prefilled on the next visit; payment fields are never persisted.

Submitting the payment step posts the order to the backend via `submitOrder` (`src/services/orders/orders.ts`), which maps the flat form state to the backend contract (`src/types/orders`), retries network failures and 5xx up to three times, and never retries a 4xx. What the checkout does with each outcome is the part worth preserving:

- **Created** → shows `OrderConfirmation` (replacing the whole checkout, not a modal, since the cart is about to be empty), saves it to `sessionStorage` (`fmc-last-order`) so a reload still shows it, and only then clears the cart. The cart is never cleared on any other path.
- **409 stale cart** → the cart is up to 14 days old, so this is expected. `reconcileCart` updates prices and drops sold-out items against the catalog already in Redux, and the checkout explains what changed and asks the customer to confirm again. It never silently charges a different amount.
- **Network failure** → the cart is kept and the customer is told to retry.

The idempotency key is tied to the payload's content, not to the page: retrying an identical order reuses it (so the backend returns the order it already created instead of duplicating it), but any change to the cart or the form mints a new one. Reusing a key after an edit would make the backend return the earlier order while the confirmation screen showed the edited cart.

The checkout reads the cart with `useAppSelector`, not `store.getState()`, so the summary re-renders when a stale cart gets repriced.

**`buildOrderPayload` se importa desde el otro repo (`FMC-0030`).** `flormorado-cafe-backend-orders/test/contract/orders.contract.test.ts` carga esta función (y lo que importa) directo desde este archivo, fuera de Jest, para probar el contrato de `/orders` con el payload real del checkout. Por eso `buildOrderPayload` y todo lo que toca en cadena (`@/utils/constants/common/forms`, `@/utils/constants/common/legal`, `@/utils/constants/store/cart`) tiene que seguir siendo TypeScript puro — sin React, SCSS ni nada que dependa de un DOM o de webpack —; si deja de serlo, ese test cruzado se rompe. Detalle en `flormorado-cafe-backend-orders/docs/pruebas-cruzadas.md`.

**WhatsApp is manual (`FMC-0024`).** Meta never approved the business verification, so nothing is sent through the WhatsApp API: the "Envíame la confirmación también por WhatsApp" checkbox, its `payment.notifyByWhatsApp` field and the WhatsApp delivery status in the orders panel were removed, and the backend ignores the field if a cached storefront still sends it. The marketing consent below stays on purpose: the business sends its news by hand from its phone with the WhatsApp app, using the list of customers who authorized them in the panel. The plain `wa.me` chat links are unrelated and untouched.

**WhatsApp marketing consent.** The "novedades y ofertas" checkbox label comes from `WHATSAPP_MARKETING_CONSENT` in `src/utils/constants/common/forms.ts`, and its `version` travels with every order (`contact.marketingConsentVersion`), checked or not. The backend stores it as proof of what the customer agreed to under Colombia's Ley 1581, so **changing the label text requires bumping the version** — otherwise old consents would appear to cover wording the customer never saw.

**BRE-B payments.** The checkout does not ask for the customer's own BRE-B key (`FMC-0025`): it was never used to charge anything, and the customer's bank already identifies them on the transfer. The order only carries `payment.method: "bre_b"`, and a storefront that still sends `breKey` is ignored by the backend. For `bre_b` orders the backend returns `instruccionesPago` (company key and account holder), and `OrderConfirmation` shows the exact amount, the key with a copy button, the holder name the customer must see in their banking app, and the order number to write in the transfer message. The key is deliberately not a frontend constant: the backend is the single source for both this screen and the confirmation email. Copy is the primary action because most customers are on the same phone that would have to scan the QR. The QR (`images.BreBQr`, `src/assets/images/payments/breb-qr.png`) must carry the **bank's own payload** — BRE-B QRs follow an interoperable standard, so one built from the key by hand moves no money. The file shipped in `FMC-0026` was re-rendered from the card the Nequi app exports: decoded, checked against the EMVCo CRC in field 63, and drawn again upright with a 4-module quiet zone, so it is byte-identical to the bank's and crisp at any size. It is static and carries no amount (field 54 is absent), which is why the customer types the value into their app. If the key ever changes, ask the bank for the new QR; don't edit this file.

**Contact**: `src/pages/Contact/Contact.tsx` is a single-step form (nombre, teléfono opcional, correo, asunto, mensaje) built directly with `Form`/`FloatingLabel`/`Form.Control.Feedback`, not through Checkout's declarative field-array system — there's only one step and no conditional fields, so the extra indirection isn't worth it. Submitting calls `submitContact` (`src/services/contact/contact.ts`), which mirrors `submitOrder`'s shape (own types in `src/types/contact`, a 15s timeout, retry on `429`/5xx up to three times, never retry a 4xx) but posts to `${ORDERS_API_URL}/contact` and resolves to a simpler `SubmitContactResult`: `"sent" | "invalid" | "unavailable"` — there's no idempotency key and no cart, so retrying just means sending the same message again. The field limits (name 3–40, email pattern plus 5–100, phone `^3[0-9]{9}$` optional, message 10–1000) match the backend's Zod schema (`flormorado-cafe-backend-orders/src/schemas/contact.ts`) on purpose — change one side and the browser will accept a message the backend 400s. Since `FMC-0020`, the backend persists the message before emailing it (so it survives an email failure and shows up in the panel), but the frontend contract didn't change: it still returns `502` if the send fails, which the frontend folds into the same retry path as a 5xx before falling back to a message that points the customer to WhatsApp. A retry with the same email and text reuses the backend's stored row instead of creating a duplicate — nothing the frontend needs to handle.

Todo el contenido de la página vive dentro de `.fmc-contact__surface`, la tarjeta blanca: el título, la frase de entrada, el formulario y el consentimiento, porque un formulario largo necesita despegarse del lienzo para leerse como una pieza y no como texto suelto. Por eso `/contacto` es la única página que no usa el componente `Title`, que se pinta a 4 rem fuera de cualquier superficie; su `h1` y el `h2` de la FAQ comparten el mixin `section-title` de `globals.scss` en vez de copiarse los valores, y la tarjeta carga con el `margin-top` que antes daba `Title` para no quedar pegada al navbar.

**Preguntas frecuentes (`FMC-0034`).** Van debajo del formulario de `/contacto`, en `src/pages/Contact/Faq/`, y no en `@/components/section`: son de esta página, igual que `OriginsExplorer` lo es de Orígenes. Tres acordeones independientes —FLORMORADO, café de origen y harina de sagú—, uno por grupo, así que puede quedar una pregunta abierta en cada grupo a la vez; las preguntas se ven todas cerradas, que es lo que permite buscarlas con Ctrl+F y lo que se perdería con un selector de grupos.

El contenido está en `FAQ_GROUPS` (`src/utils/constants/common/faq.ts`), el mismo patrón declarativo de `PURPOSE_SECTIONS`: cada respuesta son párrafos y, opcionalmente, una lista de puntos con título. Un párrafo no es un texto sino una lista de fragmentos (`IFaqParagraph`), porque casi todas las respuestas enlazan a mitad de frase; un fragmento con `url` que empieza por `/` se pinta como `Link` y cualquier otro como enlace externo en otra pestaña, así que `mailto:` y `wa.me` no necesitan marcarse. Lo que ya existe en otra constante no se reescribe aquí: el plazo de entrega sale de `DELIVERY_WINDOW`, el envío gratis de `FREE_SHIPPING_FROM` y el correo y el WhatsApp de `DATA_CONTROLLER`, porque son los mismos datos que el backend valida o que la ley obliga a publicar en un solo lugar. La respuesta de cambios y devoluciones enlaza a `/terminos-y-condiciones` en vez de repetir las condiciones: ahí sí hay que mantener una sola redacción.

El ítem «Preguntas frecuentes» del menú ya existía apuntando al inicio como provisional; ahora apunta a `/contacto#preguntas-frecuentes`, que resuelve `ScrollToTop`. Dos detalles de maquetación: el acordeón de Bootstrap se tiñe con las variables `--bs-accordion-*` en vez de con `!important`, y el chevrón se reemplaza por uno morado en los dos estados porque Bootstrap lo pinta azul al abrir; y `Accordion.Header` va con `as="h4"`, ya que por defecto es un `h2` y quedaría por encima del `h3` del grupo.

**Panel de control** (`/panel`, `FMC-0020`). Consumes `flormorado-cafe-backend-orders`'s `/admin/*` endpoints — the panel that the plan originally sketched as Worker-rendered HTML was built here instead, in React, once the backend endpoints existed and there was real interactivity to build (search, status changes, opt-out). `src/services/admin/admin.ts` holds the API layer: a single-user, no-session auth model where the panel's password *is* the bearer token (`Authorization: Bearer <clave>`), verified once against the backend and cached in `sessionStorage` (`fmc-panel-key`) for the tab's lifetime — there is no login endpoint, no expiry, and the key never persists to `localStorage`. Any request that gets a `401` (wrong key, or the key rotated server-side mid-session) throws `AdminUnauthorizedError`, which every view catches to call `onUnauthorized` and force `Panel.tsx` back to the login screen. `src/pages/Panel/` has one subfolder per tab (`OrdersPanel`, `CustomersPanel`, `ContactMessagesPanel`), each with its own `load`/`useState` data hook rather than a shared generic one — the three views differ enough (search+filter+detail+status vs. a flat opt-out table vs. a status toggle) that a forced abstraction wasn't worth it. Cada pestaña abre un modal al hacer clic en una fila, y las acciones viven en el modal, no en la tabla: cambio de estado del pedido (`OrderDetail`), baja de novedades del cliente con confirmación previa (`CustomerDetail`, que además muestra el historial de pedidos con la respuesta a la casilla de novedades como prueba del consentimiento) y marcar atendido un mensaje de contacto (`ContactMessageDetail`, que lee el mensaje de la lista del panel en vez de una copia, para reflejar el cambio al recargar). Desde `FMC-0028` el modal del cliente tiene además la **supresión de datos** (`suppressCustomer`), con su propia confirmación en dos pasos: el estado `confirming` dejó de ser un booleano y dice qué acción se está confirmando. El texto de esa sección no es relleno — dice que se borran la ficha y los mensajes pero **no los pedidos**, que conservan los datos del cliente porque son soporte contable. Al negocio le van a preguntar si borró todo, así que esa redacción tiene que seguir siendo exacta y coincidir con lo que dice la política en `/politica-de-datos`. Un cliente suprimido se muestra como «Datos suprimidos» en la lista y pierde el botón de baja de novedades, que ya no aplica.

La baja de novedades se queda en el panel porque el checkout solo permite retirar el consentimiento al hacer un nuevo pedido: un cliente que no vuelve a comprar no tendría cómo revocarlo, y la Ley 1581 exige poder hacerlo en cualquier momento. Pedidos y Clientes comparten `PanelFilters` (buscador de texto + un selector: estado del pedido / novedades del cliente): manda un único `q` al backend, que lo compara contra los datos con que se ubica a alguien (pedido, documento, celular, correo, nombre), y la búsqueda se dispara al enviar el formulario, no en cada tecla. Cada panel recuerda los filtros aplicados para recargar con ellos tras una acción. El backend recorta a 50 filas, así que `countLabel` muestra "Mostrando 50 de 120" para que el recorte no pase inadvertido; todavía no hay "ver más", se llega al resto afinando la búsqueda.

`nextOrderStatuses` (`src/utils/constants/admin/orders.ts`) duplicates the backend's status-flow table (`flormorado-cafe-backend-orders/src/utils/constants/orders.ts`) to decide which status buttons to show — same "duplicate validation on both sides" pattern as the phone regex, and the backend is what actually enforces it with a `409` if the panel is wrong.

One React-specific gotcha worth knowing: this repo's `eslint-plugin-react-hooks` (v7) enables `set-state-in-effect`, which errors on a `useEffect` that synchronously calls a function whose body sets state before any `await` — the classic "fetch on mount" `useEffect(() => { load() }, [load])` trips it, even though nothing else in this codebase had hit that pattern before the panel (no other page fetches on mount). The fix used throughout `src/pages/Panel/` is `useEffect(() => { void Promise.resolve().then(() => load()) }, [load])`: deferring the call to a microtask satisfies the rule (state is set from a callback, not synchronously in the effect body) without changing behavior.

**Páginas de relato (`FMC-0032`, `FMC-0033`).** `/nuestro-proposito` (`src/pages/Purpose/`) y `/origenes` (`src/pages/Origins/`) son la misma pieza con distinto contenido, así que la maquetación vive en `@/components/section` (`Story.tsx` + `Story.scss`, prefijo `.fmc-story`) y cada página solo aporta sus textos: `StoryPage` es la franja beige a todo el ancho con el contenido dentro, `StoryLead` la frase de entrada en Economica morada —junto a una ilustración, o sola y centrada si no se le pasa `image`, que es como abre Orígenes—, `StorySections` las secciones y `StoryCta` el bloque morado de cierre. La primera, la página institucional, antes estaba enlazada en el menú a `/origenes`; con ella desapareció `About` (`/sobre-nosotros`), que era una página vacía con un título prestado y ya no tenía a qué responder. Orígenes arranca con los cafés de origen y termina con el mapa de los tres orígenes.

El contenido no está en el JSX: vive en `PURPOSE_SECTIONS` y `ORIGINS_SECTIONS` (`src/utils/constants/common/`), listas de `IStorySection` con su encabezado, párrafos, ilustración y, opcionalmente, una cita o una lista de puntos. `StorySections` las recorre y alterna el lado de la ilustración, así que se agrega, se reordena o se reescribe una sección sin tocar maquetación —el mismo patrón declarativo de `CONTACT_FORM_FIELDS` en el checkout—. Dos campos opcionales cambian la forma: sin `question` la sección es solo texto, que es como se entra a lo que viene después, y sin `image` se pinta en una sola columna centrada, caso en el que el zigzag de las demás la salta para no dejar dos seguidas del mismo lado. `highlightsLayout` decide si los puntos van junto al texto (`"list"`) o a todo el ancho como tarjetas (`"cards"`, los tres pilares de impacto). El diseño reusa el lenguaje del blog —banda de sección sobre el lienzo, títulos en Economica sobre café y tarjetas claras que se levantan al pasar el cursor— para que no parezcan páginas de otro sitio.

**Las imágenes son las ilustraciones del repo.** Hubo un primer intento con fotos de Wikimedia Commons y se descartó: la marca tiene su propio trazo y una foto genérica desentonaba más que una ilustración que no venga exactamente a cuento. Así que las páginas reparten las de `src/assets/images/illustrations/`, aunque alguna no corresponda al texto, hasta que entren las definitivas; sustituir una es cambiar el `import` en `purpose.ts` u `origins.ts`. Dos cosas que conviene no romper. La primera: se importan en esos archivos, no en `media/images.ts`. Ese archivo exporta un único objeto `images` del que el pie usa el logo, así que todo lo que entre ahí queda atado al chunk inicial; las seis ilustraciones viejas ya estaban en ese objeto desde antes y por eso siguen viajando en el inicial de todos modos, pero las que se importan directo cuelgan del chunk perezoso de su página, que es donde se comprobó que quedan. La segunda: la caja es fija y la ilustración se ajusta dentro con `object-fit: contain`, nunca `cover`, porque son trazos sobre fondo transparente y varias son muy verticales —`coffee_plant.svg` es 1:3,6— así que recortarlas las destroza.

**El mapa de los tres orígenes (`FMC-0033`).** La parte interactiva de `/origenes` vive en `src/pages/Origins/OriginsExplorer/`, junto a su página y no en `@/components/section`, porque es de esta página y no del formato de relato —el mismo criterio con que `src/pages/Panel/` tiene una carpeta por pestaña—. Son tres piezas: `ColombiaMap` pinta el mapa, `OriginDetail` la ficha del origen elegido y `OriginsExplorer` guarda cuál está seleccionado. El contenido está en `ORIGINS` (`src/utils/constants/common/origins.ts`), y el `id` de cada origen es a la vez la llave del departamento y del marcador en el mapa: si se agrega un cuarto origen hay que agregar su departamento a `colombia.ts` con el mismo `id` o el mapa se queda sin pintarlo.

Quien manda en la selección son los **botones**, no el mapa: el SVG va con `role="presentation"` y sin foco, así que el teclado y los lectores de pantalla pasan solo por los botones y el mapa es un atajo con el mouse. Por eso la ficha es un `aria-live="polite"`: al pulsar un botón no hay navegación y, sin esa región, nada anunciaría que el contenido cambió. En móvil el mapa se encoge y queda arriba, centrado; en escritorio se queda pegado (`position: sticky`) mientras se lee la ficha, que es más larga.

**`colombia.ts` es generado, no se edita a mano.** Las siluetas salen de [Natural Earth](https://www.naturalearthdata.com/) —dominio público, sin atribución exigida, que es justo lo que descartó a los mapas de Wikimedia y de npm, todos CC BY— proyectadas en equirectangular sobre la caja del país y simplificadas con Douglas-Peucker hasta unos 6 KB en total, que viajan en el chunk perezoso de la página. Los marcadores son las coordenadas reales de Somondoco, San José y Planadas, y se comprobó que cada uno cae dentro de su departamento ya simplificado. Para rehacerlo o agregar un departamento hay que volver a generarlo desde Natural Earth, no mover números a ojo: el `viewBox` sale de la caja del continente, así que tocar un punto desencaja los demás.

**Enlaces a una sección.** El menú puede apuntar a una sección concreta con `ruta#id` —`/nuestro-proposito#nuestra-historia`—, donde el `id` es el de la sección en la lista de esa página. Con `HashRouter` la barra de direcciones termina en `/#/nuestro-proposito#nuestra-historia` y React Router lee ese segundo `#` como `location.hash`, así que quien resuelve el salto es `ScrollToTop` (`src/components/common/ScrollToTop/`): sin ancla sube al tope como siempre, con ancla baja hasta ese elemento. Como la página destino se carga con `React.lazy`, al llegar desde otra ruta la sección todavía no está en el DOM, así que reintenta cada 50 ms hasta tres segundos; si el ancla no existe se rinde en silencio y la página se queda donde está.

**La barra acompaña el recorrido (`FMC-0036`).** Es `position: sticky` —no `fixed`, que obligaría a reservarle una franja equivalente en cada pantalla— y `useHideOnScroll` la aparta al bajar y la devuelve al subir, sin esperar al tope. Tres cosas que costaron encontrarse y conviene no deshacer: dentro de la zona de reposo (los primeros 120px) la barra se muestra **siempre**, haya llegado o no un evento de movimiento, porque sin eso al llegar a una pantalla corta se quedaba escondida sin nada que la devolviera; el hook recibe el `pathname` y reinicia `hidden` al cambiar de ruta, durante el render y no en un efecto, que es el patrón de React para ajustar estado cuando cambia una entrada y además esquiva `set-state-in-effect`; y con el menú abierto la barra no se va, o el panel quedaría colgando de algo que ya no está.

El alto lo impone `--fm-navbar-h` y no el contenido, porque de ese número dependen dos cosas: el `scroll-padding-top` que compensa **todas** las anclas de una vez —lo honran tanto el `scrollIntoView` de `ScrollToTop` como el de `scrollToSection`— y el margen negativo con el que la portada sube por detrás de la cabecera. Si cambia el alto de la barra hay que ajustar la variable.

**Los desplegables son `Dropdown` (`FMC-0036`).** El popover a mano de antes no tenía teclado: era un `Nav.Link` con `onClick`, sin `aria-expanded`, sin Escape ni flechas. El componente de react-bootstrap trae todo eso de fábrica; encima se le añade la apertura al pasar el cursor, con retardo de intención para que no parpadee al cruzar la barra, y el clic en el título sigue llevando a la página. Es `Dropdown` suelto y **no `NavDropdown`**, que es lo primero que se probó: `NavDropdown` no deja poner clases en el disparador, y el disparador tiene que llevar `fmc-navbar-link` para ser un enlace de la barra como los demás — sin eso quedaban desalineados con «Inicio» y con la flecha que Bootstrap añade por su cuenta. El aspecto del panel es el de siempre: beige, 250px, morado al pasar por encima.

**Navbar: un modo sólido y uno superpuesto (`FMC-0035`).** Por defecto el navbar es el que antes vivía solo en las páginas de relato —beige sólido, dentro del flujo, con el logotipo escrito— y en escritorio se invierte entero a morado al pasar el cursor: letras beige y el botón «Ir a la tienda» en beige con el carrito sin el filtro que lo volvía blanco. La excepción es el inicio, que abre con un video a todo el ancho: esas rutas van en `OVERLAY_NAVBAR_URLS` (`src/utils/constants/common/data.ts`) y ahí la barra se superpone al video, cambia el logotipo escrito por el símbolo en beige —la palabra repetiría la del propio hero— y la cinta de anuncios se vuelve transparente con ella. No es transparente del todo: lleva un velo degradado que se desvanece hacia abajo, porque el texto es beige y el video cambia de fotograma, así que sin él la barra se vuelve ilegible cada vez que pasa una zona clara. La inversión a morado funciona igual en los dos modos sin escribirla dos veces: `.flormorado-navbar:hover` pesa más que `.flormorado-navbar--overlay`, así que gana por especificidad. Desapareció en cambio `SOLID_NAVBAR_URLS` y con él el modo translúcido beige, que solo tenía sentido mientras había una foto de fondo.

**Legal pages (`FMC-0027`, `FMC-0029`).** `/politica-de-datos` (`src/pages/Privacy/Privacy.tsx`) is the Política de Tratamiento de Datos Personales required by Colombia's Ley 1581 de 2012 and Decreto 1377 de 2013 — it is a compliance document, not marketing copy, so every section maps to something the law demands (identification of the responsable, purposes, rights, the consultation/claim deadlines, retention, international transfer) and it has to keep describing what the code actually does. If the checkout starts collecting a new field, a new provider gets added, or a retention period changes, this page changes with it.

The responsable's identification lives in `DATA_CONTROLLER` (`src/utils/constants/common/legal.ts`), never inline in the page, because the law requires the same data in several places and a stale copy of it is a legal problem, not a typo. These are legally demanded values: a placeholder has no business being there. `DATA_POLICY.version`/`effectiveDate` are what the page publishes as its vigencia; bump both on a substantial change, which the policy itself promises to announce before applying. Since `FMC-0028` that version also **travels with every order and contact message** (`contact.privacyPolicyVersion`, and the field of the same name on the contact payload) and the backend stores it as the proof of the general authorization — the acceptance is implicit, so the stored version is the whole of the proof. Bumping it on a reworded policy is therefore not bookkeeping: skip it and the rows claim customers saw text they never saw. The panel shows it next to the marketing consent in the customer's order history.

`/terminos-y-condiciones` (`src/pages/Terms/Terms.tsx`) is the other half, under a different law: the Estatuto del Consumidor (Ley 1480 de 2011, reformed by Ley 2439 de 2024). Three things in it are obligations, not copy, and they are satisfied elsewhere in the app — change one and the page starts promising something the storefront doesn't do:

- **The delivery window** (`DELIVERY_WINDOW`) must be shown before the purchase closes (art. 50) and is repeated in the backend's confirmation email, which doubles as the acuse de recibo. The two constants are duplicated across repos on purpose, like the pricing rules. Miss the promised window and the customer may cancel and demand a refund within 15 calendar days.
- **The contact form hands back a radicado with its date and time** (art. 50 lit. g). It comes from the backend's `POST /contact` response; the `sent` outcome carries it optionally so an older backend doesn't break the form.
- **A visible link to the Superintendencia de Industria y Comercio** (`CONSUMER_AUTHORITY`, in the footer) is required by the parágrafo of art. 50.

`TERMS.version` travels with every order just as `DATA_POLICY.version` does, and the same rule applies: bump it whenever the terms change in substance, or the stored rows claim the customer accepted conditions they never saw. Both pages share the `.fmc-legal` layout, which lives in `src/styles/styles.scss` because two pages use it.

The link to the policy must stay wherever personal data is collected (the checkout's "compra segura" alert and the contact form's consent line) — that notice is what makes the authorization valid, so removing it is a legal regression, not a copy tweak. Note this is separate from `WHATSAPP_MARKETING_CONSENT`: the policy explains the marketing consent, but the checkbox's own wording and version live in `forms.ts` and are versioned on their own.

**Styling**: Sass/SCSS co-located per component/page (`Component.scss` next to `Component.tsx`), plus global variables/mixins in `src/styles/globals.scss` and app-wide rules in `src/styles/styles.scss`. Bootstrap 5 / React Bootstrap is used alongside custom SCSS.

**Qué va en `globals.scss` y qué en `styles.scss` (`FMC-0035`).** `globals.scss` solo puede tener cosas que **no emitan CSS**: variables de Sass y mixins. Todo lo que emita —un `@font-face`, un `:root`, un `@keyframes`, una regla— se duplica una vez por archivo que haga `@use`, y son 35, porque `style-loader` compila cada SCSS de componente por separado. Por eso el `@font-face` de Economica, las custom properties (`--fm-duration`, `--fm-easing`, `--fm-radius`, `--fm-shadow`, `--fm-shadow-strong`) y los `@keyframes` compartidos (`fadeInUp`, `fadeIn`) viven en `styles.scss`, que `src/index.tsx` importa una sola vez. Antes `fadeInUp` estaba declarado dentro de `ProductGallery.scss` y lo usaban también `Toast.scss` y la tarjeta de producto: como el CSS se inyecta por chunk, el toast del inicio se quedaba sin animación hasta que el visitante entraba a un producto.

**El lienzo es beige y hay tres planos (`FMC-0035`).** Se quitó la foto de flor que `#root` pintaba a pantalla completa en escritorio —2 MB que además se repintaban en cada scroll por el `background-attachment: fixed`— y con ella la razón por la que cada pantalla se inventaba su propia superficie. En su lugar hay una escala de tres superficies en `globals.scss`, de atrás hacia adelante: `$fm-surface-page` (#f4ece0, el lienzo de `#root`), `$fm-surface-section` (el beige de marca, para bandas a todo el ancho como `.fmc-story` o la sección de categorías) y `$fm-surface-card` (casi blanco, para tarjetas). Sin esos tres planos un sitio entero en beige se ve plano, porque todo queda al mismo nivel. El lienzo no usa `$principal-beige-oscuro`: ese es un gris frío y, debajo del beige cálido de la marca, lo ensucia. Los bordes y las sombras (`$fm-border-soft`, `$fm-shadow-sm/md/lg`) van en tinta café y no en negro, por lo mismo.

**`.fm-container` va sin `overflow` (`FMC-0036`).** Tenía `overflow-x: hidden; overflow-y: auto`, y cualquier valor distinto de `visible` lo convierte en contenedor de recorte: los `position: sticky` de dentro —el navbar y el mapa de `/origenes`— quedan entonces a merced del navegador. Se probaron los tres casos: con `hidden` no se pegan en ninguno, con `clip` se pegan en unos sí y en otros no, y sin `overflow` funcionan en todos. Antes de quitarlo se comprobó ruta por ruta que nada desborda a lo ancho, así que no había nada que recortar; `max-width: 100vw` se queda de red de seguridad. Si alguna vez aparece un desbordamiento horizontal, se arregla en el elemento que lo causa y no volviendo a poner `overflow` aquí.

**El logotipo es texto, no imagen (`FMC-0035`).** `Wordmark` (`src/components/ui/Wordmark/`) escribe «FLORMORADO» en Economica y «CAFÉ» debajo en Source Sans 3 con tracking, que es lo que decía el PNG `logo-nombre.png`. Al ser texto hereda el color de donde esté, y eso es lo que permite usar el mismo componente en el navbar beige, en el navbar invertido a morado y en el pie morado sin tener un archivo por fondo; los cuatro PNG de logo que cubrían esos casos salieron del objeto `images` y con ellos del chunk inicial. `Isotype`, al lado, hace lo mismo con el símbolo: el PNG trae el grano en morado y las hojas en verde, así que sobre fondo morado se perdería, y se pinta como `mask-image` con `background-color: currentColor`. Eso funciona porque el archivo tiene el fondo **y las líneas interiores** en transparente —comprobado leyendo su paleta: solo hay dos colores opacos y ningún blanco— así que la silueta conserva sus huecos. Los dos toman el tamaño del `font-size` del contexto, porque se miden en `em`. Un detalle que se nota al tocarlo: el `letter-spacing` de la segunda línea también separa después de la última letra, así que lleva un `margin-right` negativo del mismo valor para quedar centrada bajo la primera.

**El pie es morado (`FMC-0035`).** Con el sitio entero en beige, un pie beige no cerraba la página: se leía como una sección más. Va en `$principal-purple` con texto beige. Dos cosas que arrastra y conviene no deshacer: el logo tiene que ser el `Wordmark` y no el PNG, porque ese PNG trae el fondo beige quemado y sobre morado saldría como un recuadro claro; y los iconos no pueden ir como `<img>` con un filtro encima. Los originales son insignias con su color de marca —el azul de Facebook, el degradado de Instagram, el círculo con degradado del sobre— así que `brightness(0) invert(1)` los convertía en una mancha blanca; el único que se salvaba era el teléfono, que ya era un trazo suelto. Al lado de cada uno hay ahora una versión `-mono.svg` de un solo trazo (las de marca, de Simple Icons, CC0) que se pinta con `mask-image` y `background-color`, así que el color lo decide quien la usa. Los originales a color siguen en su sitio porque `/contacto` y el botón flotante de WhatsApp los usan sobre fondo claro.

**El inicio abre con video (`FMC-0035`).** `src/components/section/Hero/` reemplazó al `Banner`, que en escritorio era solo el PNG del logotipo centrado a 93vh **sobre la foto de fondo**: al quitar la foto habría quedado un hueco. Es un `<video autoplay muted loop playsinline>` a todo el ancho con su `poster`, un velo degradado para que el texto se lea sobre cualquier fotograma, y encima el logotipo, una frase y dos botones.

**Hay un material por orientación y la portada adopta su proporción.** `HERO_MEDIA` (`src/utils/constants/media/hero.ts`) tiene una entrada `landscape` y otra `portrait`, y el componente elige con `useMediaQuery("(orientation: portrait)")` —por orientación y no por ancho, porque lo que decide qué encuadre entra sin recortarse es la forma de la pantalla—. La sección no tiene altura fija: toma la del material con `aspect-ratio`, así que `object-fit: cover` no recorta nada. Por eso **el `aspectRatio` declarado tiene que ser el del archivo**, no una aproximación: declarar `16 / 9` para una foto de 1920x845 le cuesta un 20% por los lados. El único recorte que queda es el del tope `max-height: 92vh`, que evita que la portada crezca por encima de la ventana y deja asomar la sección siguiente; en un móvil pequeño eso son un 7%. El `<video>` lleva `key={media.video}` porque sin él el navegador se queda con la fuente anterior justo cuando se gira el dispositivo.

Tres cosas más que conviene no deshacer: el video y el póster viven en esa constante y **no** en `images`/`videos`, para que viajen en el chunk perezoso del inicio y no en el inicial —el pie importa `images`, así que todo lo que entre ahí lo descarga también quien llega a una página legal—; con `prefers-reduced-motion` se pinta el póster y no se monta el video, que es algo que el CSS no puede decidir solo y por eso existe `useMediaQuery`; y el material de hoy es provisional, pensado para reemplazarse por sus URL de Cloudinary —donde ya viven las imágenes de producto— sin tocar el componente, que es lo que sacará esos 3,4 MB de dentro del paquete. Hoy `landscape` no tiene video, solo el póster apaisado, hasta que exista el definitivo.

**Anti-abuse: Turnstile (`FMC-0021`).** `src/components/common/Turnstile/Turnstile.tsx` renders Cloudflare's captcha under the checkout accordion and above the contact form's submit button, with `appearance: "interaction-only"` so it stays invisible unless Cloudflare can't decide silently. It loads `api.js?render=explicit` once (a blocked or failed script marks the widget as failed instead of throwing) and exposes `getToken()` / `reset()` through a `ref`. Both pages call `getToken()` right before `submitOrder`/`submitContact`, pass it as `{ turnstileToken }` (sent as `X-Turnstile-Token`), and call `reset()` afterwards, because a token is single-use. Three things worth preserving:

- **No site key, no widget.** If `TURNSTILE_SITE_KEY` is unset the component renders nothing and `getToken()` resolves `undefined`, so requests go out without the header. That is what makes the two deploys independent: the backend only enforces the token once `TURNSTILE_SECRET_KEY` exists there.
- **Retries reuse the same token.** `submitOrder`/`submitContact` resend it on every retry; the backend verifies it with the order's idempotency key (or a hash of the contact message), so Cloudflare returns the original result instead of "token already used". A new token is only requested after the whole attempt finishes.
- **`403` is its own outcome.** It maps to `{ kind: "verification_failed" }`, never retried, with copy that tells the customer to reload and check for content blockers. It must not fold into `unavailable`, or a customer whose captcha is blocked would be told to "check their connection".
